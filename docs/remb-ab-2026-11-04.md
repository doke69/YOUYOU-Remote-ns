# REMB A/B 构建门控说明（2026-11-04）

## 目的

用户新日志中 Q6 50M 实际中位约 7.3M、100M 约 13.4M，但两次运行的 field 8 与 REMB 同时变化，无法把差异归因于 REMB 主动提交。本门控只把“Client 是否主动提交 REMB”做成构建差异，其余用户设置保持不变。

## 构建开关

`CMakeLists.txt` 新增：

```text
UU_REMB_FEEDBACK=ON   默认；Client 主动 REMB 路径保持启用
UU_REMB_FEEDBACK=OFF  阻止 Client 主动 requestBitrate
```

NRO 的 `UURemote-ns.manifest.json` 增加 `UU_REMB_FEEDBACK` 选项，便于核对实际构建身份。

## 两种构建的行为

| 项目 | OFF | ON |
|---|---|---|
| `applyBitrateCap` 入口 | 直接返回，不调用 `video_->requestBitrate` | 原逻辑 |
| 本地 RTCP SSRC/CNAME | 不变 | 不变 |
| SR 后的 RR+SDES(CNAME) | 不变，仍由依赖 RTCP 会话发送 | 不变 |
| 首包前的目标门控 | 不涉及主动提交 | 原逻辑 |
| field 8 / quality / 预设 / 分辨率 / fps | 不变 | 不变 |
| 配置持久化 | 不修改、不清除，沿用现有用户设置 | 同左 |
| 每会话日志 | `remb-experiment-disabled` 一次 | `remb-experiment-enabled` 一次 |

日志在 `beginPeer` 建立视频轨之前写入，因此首包到达前即可确认本次构建属于 A 组还是 B 组；使用会话布尔标记，不会每 tick 重复。OFF 构建不会清除或改写现有用户配置；两种构建都使用同一套用户设置。

## A/B 操作

1. 使用相同账号、设备、画质/分辨率/fps/码率档位、播放缓冲和 vsync。
2. A 组使用 `-DUU_REMB_FEEDBACK=OFF` 构建，确认日志出现 `remb-experiment-disabled`。
3. B 组使用默认 `-DUU_REMB_FEEDBACK=ON`（或显式 ON）构建，确认日志出现 `remb-experiment-enabled`。
4. 两组分别记录 `stream-rate actual-mbps`、`remb-target-bps`、`remb-sender-ssrc`、`remb-media-ssrc`、`feedback`，以及 PC 侧 Incoming REMB / SetBitRate（如有）。
5. 只有在两组 field 8、quality、分辨率、fps、缓冲完全一致时，才能把差异归因于 Client 主动 REMB。

注意：OFF 仍会发送 SR 触发的 `RR+SDES`（没有 REMB 子包），这是为了保留本地 RTCP 身份和既有报告路径；因此 A/B 的差异应只在 REMB 主动提交及其后续效果，而不是本地 RTCP 身份或 RR/SDES 本身。

## 未做与风险

- 本次没有构建、部署或发版；由 Codex 独立构建核验 ON/OFF 两种配置。
- OFF 不清除当前进程内已有的 REMB 目标；切换到 OFF 构建应使用新进程/新会话，实际部署时按新构建启动即可。
- 本门控不实现 transport-cc，也不改变 PC 行为；若 B 组仍不升码率，需要 PC 侧证据再判断后续方向。
- 仍需真机抓包确认 REMB 的实际 sender/media SSRC、DLSR 和 PC 响应；日志只证明本地路径与开关状态。
