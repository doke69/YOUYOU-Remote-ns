# v0.1.62：为视频UDP缓冲预留BSD内存

## 已取得的真机证据

v0.1.61的schema13回传匹配了实际已选host UDP端口：

| 项目 | 结果 |
|---|---|
| 实际接收缓冲 | 42,240字节（41.25KiB） |
| 实际发送缓冲 | 9,216字节（9KiB） |
| 原1MiB接收缓冲设置 | 失败，errno105 |
| 原1MiB发送缓冲设置 | 失败，errno105 |

本机构建SDK的 `sys/errno.h` 将105定义为 `ENOBUFS`。旧代码忽略了设置结果，因此此前不能声称1MiB缓冲已经生效。这是实际视频ICE套接字的创建回读，不是启动时临时探测套接字，也不等于内核丢包计数。

小接收缓冲与大关键帧突发缺包的现象相符，但尚不能据此断言它解释所有卡顿。

## 修正

程序原来使用默认socket初始化。本版在创建任何网络套接字之前复制SDK默认配置，仅将 `udp_rx_buf_size`、`udp_tx_buf_size` 各设为1MiB。TCP设置、BSD会话数及缓冲效率保持原值。

[libnx的BSD初始化实现](https://github.com/switchbrew/libnx/blob/master/nx/source/services/bsd.c)按配置计算、分配并注册共享缓冲内存。按当前SDK默认的TCP上限和效率计算，本版约预留10MiB，比原配置增加约7.8MiB；没有手动固定共享内存地址或绕过服务权限。

如果较大池初始化失败，尝试原默认配置保留可用性；实际套接字回读仍会暴露较小缓冲。如果两次初始化均失败，在既有错误界面显示初始化错误，而非继续假设网络可用。

保留v60的按RTT组帧期限、v59编码队列保护、播放缓冲及用户配置、显示/解码/码率/关键帧请求策略。schema13字段不变，接收器增加0.1.62版本接纳。没有为了掩盖问题降低画质或增加播放缓冲。

## 接受标准与限制

下一次运行首先检查：实际端口匹配，收发缓冲是否达到1,048,576字节，设置错误是否归零。此结果只能证明缓冲申请成功，仍需检查缺包、等待IDR、新画面间隔与体感。

较大缓冲可能在接收线程持续落后时保留更多排队数据；保留原有接收期限和队列保护来限制陈旧内容。无线环境、驱动或发送端问题仍可能存在。

## 后续真机结果

Lite已匹配实际UDP套接字，收发缓冲均1,048,576字节，设置错误码均0。排除启动阶段后约79秒中，峰值实际28.4 Mbps；新增缺口、NACK、RTX、接收丢弃及等待IDR均为0。用户反馈“长卡顿已消失，整体流畅”。此为单轮场景证据，不能外推为所有网络或100 Mbps均稳定。未运行测试套件。
