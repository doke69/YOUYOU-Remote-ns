# v0.1.8 — 花屏 / 参考帧丢失修复

本版针对真机串流出现的「花屏」（画面撕裂、彩色块、条带、部分区域错乱）问题，从接收与解码两端加固。
电脑端画面正常，问题在 Switch 客户端的 H.264 参考帧丢失与恢复机制。

## 原因分析

`花屏` 的典型成因是 **RTP/UDP 丢包或解码队列丢帧后，H.264 参考帧（参考图像）丢失**：

- 解码器收到缺少参考帧的 P 帧时只能做错误隐藏，输出大块彩色噪点 / 条带；
- 上游 v0.1.6 既没有向发送端请求关键帧（RTCP PLI/FIR），也不会在丢帧后等待 IDR，
  因此画面会一直保持花屏，直到发送端自己周期性发 IDR 才恢复；
- 解码队列只有 8 帧且溢出时直接清空，会进一步打乱参考帧序列；软件解码 1080p 较慢时更容易触发；
- NVDEC 硬件解码使用 2 个解码线程，部分 hwaccel 不支持帧级多线程，也可能输出异常。

## 修复

1. **主动请求关键帧（RTCP PLI）**：连接建立后立即请求一次 IDR，之后在
   解码器报错（`decode_error_flags` 非 0）、画面停滞超过 1.5 s、每 4 s 周期时，通过
   `rtc::Track::requestKeyframe()` 请求新关键帧；发送端支持 PLI 时可在几百毫秒内恢复干净画面。
2. **不显示损坏帧**：解码器标记为损坏（丢失参考 / 位流错误）的帧不再覆盖最后一帧好画面，
   避免花屏闪烁；若连续 2 s 没有干净帧则恢复显示，防止永久冻结。
3. **队列溢出改为「丢弃 + 请求关键帧」**：队列上限提高到 16，溢出时清空积压、刷新解码器并请求 IDR，
   而不是把断裂的参考序列继续喂给解码器。
4. **NVDEC 单线程**：硬件解码线程数固定为 1（软件解码 3 线程），规避 hwaccel 帧级多线程导致的异常。
5. **解码路径可配置**：新增 `sdmc:/switch/UURemote-ns/config.ini` 的 `decoder=auto|software|hardware`
   （或环境变量 `UU_DECODER`）。真机 NVDEC 未经验证，若硬件解码仍有异常可改用 `decoder=software` 验证。
6. **覆盖层状态行**显示当前解码方式、画面尺寸、解码错误与丢帧计数，便于真机定位。

## 验证

- 交叉编译与 NRO 打包通过，NRO 版本 0.1.8。
- 本机原生测试 6/6 通过；`tests/switch_sctp_layout_test.py` ABI 检查通过。
- 真机复测仍需在 23.0.1 + AMS 1.12.1 上确认：连接后覆盖层应显示「软件解码/NVDEC 硬件解码 · 1280x720」，
  花屏应在 1 秒内自动恢复为正常画面；若仍花屏，请记录覆盖层状态行与 `connection.log`。
