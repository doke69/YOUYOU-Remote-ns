# v0.1.60：按实测延迟限制组帧等待

本版针对缺包帧长时间阻塞后续帧的候选修正。尚无本版本的真机效果结论。

## 本轮证据

- v0.1.59 的新起点后，高码率场景解码队列没有整批清空，接收与解码数量一致，但仍出现接收恢复停顿。
- 16ms 播放缓冲对照中，60秒平均实际码率约16.0Mbps，接收与解码均3371帧，接收器丢弃202帧，其中等待IDR177帧。此窗口出现最高约1.31秒新画面提交间隔。不能仅凭此对照认为16ms更好或更差。
- 退出事件反复记录缺包帧等到约600ms才退休，并积压约三四十帧。正常已解码画面等待提交的中位数约20ms；两类等待不可混淆。
- 复核完整代码发现 `process()` 尾部已有 `if (waitingIdr_) pli(now)`。此前“等待关键帧时漏掉重试”的初判撤回，本版不重复添加该逻辑，也不改700ms PLI节流。

## 唯一传输行为调整

- 尚未测得路径RTT时继续采用原配置的组帧期限，默认600ms。
- 测得RTT后，预算取 `4 × max(路径RTT, 已有足够样本的补包往返估计) + 40ms`，约束在160–600ms，并且不超过用户原有 `receiver_deadline_ms` 上限。
- 目的：低延迟路径给补包保留多轮机会，同时减少无效旧帧长时间挡住新帧；高延迟路径保留较长等待空间。
- `receiver_events.csv` 的 `deadline_ms` 列记录事件发生时有效预算；`receiver_v2.txt` 额外记录 `effective_deadline_ms` 与 `rtt_measured`。
- 仍只交付结构完整的访问单元，保留原有安全IDR恢复边界，不放行残缺帧。

## 保留内容

v59的32帧/8MiB编码队列保护、GPU显示、H.265、码率控制、默认设置、已保存的配对和画质、播放缓冲、显示调度及菜单均不改。schema12字段不变，电脑接收器增加0.1.60版本接纳。

## 边界

这不是Wi-Fi丢包根因的证明或修复。更短组帧期限可能放弃较晚到达的有效补包，增加恢复关键帧需求。需要用实际接收丢弃、等待IDR、新画面间隔及体感核验，不能只以平均解码耗时判断。

本轮检查为源码审阅、编译及产物/安装回读；未运行测试套件。真机结果在后续检查点记录。

网络初始化默认值核对来源：[libnx socket.c](https://github.com/switchbrew/libnx/blob/master/nx/source/runtime/devices/socket.c)。本版没有更改socket初始化或收发缓冲大小。
