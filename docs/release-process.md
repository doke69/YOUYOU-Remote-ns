# 维护与发布核对清单

本文用于后续源码快照维护。默认发布内容是**完整公开源码**；NRO、ELF、NSP不进入源码仓库，也不自动创建二进制附件。

## 1. 选定唯一版本基准

- 应用版本只在 `CMakeLists.txt` 的项目版本定义中递增。
- 常规构建让 `scripts/build.ps1` 从 CMake 读取版本；候选构建可临时使用独立标签，但不能把候选标签写成正式发布版本。
- README、CHANGELOG、项目状态、使用手册、构建指南、第三方清单和对应 `docs/releases/` 页面必须指向同一当前版本。
- 版本历史页保留旧事实，但旧的“当前”“待合并”“尚未实现”等状态要标明所属版本和日期。

## 2. 更新文档事实

- 更新说明区分源码已实现、编译验证、设备安装、真机行为和未覆盖环境。
- 不把请求发送/ACK写成主机已应用；不把界面计时写成纯硬件耗时；不把一次场景结果外推成普遍保证。
- 同步操作手册中的按键、默认配置、页面名称、文件路径和故障处理。
- 同步项目状态表、第三方来源与许可、非官方身份、认证材料和分发边界。
- 删除公开文档中的个人绝对路径、账号/地址、密钥、令牌、配对数据及未经授权的原版资源。

## 3. 检查仓库和发布内容

- 确认当前分支和工作区差异；只暂存本次明确审核过的文件。
- 检查没有提交 `signing.key`、会话/配置、原始日志、固件、APK、NRO/ELF/NSP、构建目录和本地工具。
- 检查许可证、NOTICE、第三方资源来源和依赖覆盖清单完整。
- 文档提交运行 `git diff --check`，核对所有新增链接和版本引用。
- 源码快照发布前检查忽略规则之外的完整源树，避免只更新部分目录而删除仍需的资源、字体、着色器或许可证。

## 4. 提交与标签

- 文档维护若没有程序功能变化，不递增应用版本，不创建新的应用版本标签；使用描述清楚的独立提交。
- 程序快照发布时才建立对应版本标签，并确保标签、CMake、NACP、应用内版本与发布说明一致。
- 默认使用普通快进推送；除非用户明确要求且完成备份，不改写已发布历史。
- 推送后核对默认分支提交、版本标签和公开文件清单。
- 若计划发布二进制，另行核查内嵌认证材料、第三方授权、对应源码及许可要求；源码发布授权不自动覆盖二进制分发。

## 5. 验证记录

每次发布说明至少记录：提交/标签、改动范围、执行过的检查、未执行的构建或实机测试、已知限制，以及二进制是否发布。没有执行的检查明确写“未执行”，不要沿用旧版本的通过结果。
